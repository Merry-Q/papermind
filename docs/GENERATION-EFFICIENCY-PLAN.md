# paperMind 交互讲解生成效率与长 PDF 方案

日期：2026-10-25。状态：基于当前代码和运行记录的开发方案，尚未实施性能改动。正在运行的 cross-domain-retest 保持原代码、提示词和预算，先完成整批再集中改动。原呈现升级和默认发布任务仍需完成。

## 1. 结论与不变要求

优化实际生成时间和首次可阅读时间，两者分别计量。优先消除串行等待、重复证据传输、重复视觉取证和无关重生成；保留核心编写模型与所有质量门槛。

不以减少全文覆盖、缩短必要讲解、减少有用状态、降低模型档次、跳过图表核验或仅查默认状态换取速度。阅读优先级只改变任务执行顺序，不能使后半篇长期不生成。

“首轮完整”的定义不变：首次标记完成时，必须已有覆盖全文核心论证、能从头读到尾的讲解和已通过检查的必要交互。用户可以提前阅读已完成部分，但界面必须明确仍在生成；渐进显示本身不算完成提速。

## 2. 当前实测与瓶颈

| 图解编写 composer | 19 | 1339.92 | 66.91 | 415785 |

计时限制：gateway 在获取并发许可前开始计时，因此 elapsed 包含部分排队及重试；并发请求累计值不能当作用户总等待时间。此轮复用原计划，planner 调用数不能代表首次生成成本。已完成六篇的任务墙钟约 214–830 秒，包含文档队列等待，也不是单篇无排队速度。

当前可定位的瓶颈：

1. `backend/presentation_jobs.py` 只有两个文档工作线程；同篇各场景在一个 for 循环中串行完成编写、浏览器、视觉、来源复核。
2. `backend/jobs.py` 的长文归纳分组、正文分组与后续核验主要串行；呈现还需等待规范正文全篇 ready。
3. 一个失败场景即使已经有正确图稿，也可能重新编写整幅，而不是仅重跑失败检查。编写是当前最贵阶段。
4. 视觉证据按任务/节点保存，同一原页可能被不同场景和复测重复读取；已通过产物复测也会再次调用视觉与来源模型。
5. 复核上下文包含大量逐状态 DOM 几何记录；坐标边界适合确定性检查，无需在事实模型中重复传递。编写上下文也混有其他节点和整页无关片段。
6. 每个浏览器检查启动独立 Node/Edge 进程；模型、浏览器、解析资源缺少独立调度和细分计时。
7. 编写或视觉输出截断会浪费整次调用。简单提高并发或输出上限不能单独解决这些问题。

## 3. 先改执行结构：按场景流水并行

```text
全文解析和论证计划
         ↓
节点 A：正文/来源通过 → 图表取证 → 图解编写 → 浏览器 ┬→ 来源复核 ┐
节点 B：正文/来源通过 → 图表取证 → 图解编写 → 浏览器 └→ 显示复核 ┴→ 节点通过
节点 C：正文/来源通过 → ……
         ↓
全文覆盖核验 + 必要交互检查全部结束 → 首轮完整 → 发布
```

- 将单篇串行循环拆成独立场景任务；结果按原 node_id 和阅读顺序归并，任务结束顺序不改变页面顺序。
- 首先沿用当前总模型并发额度 3，允许场景填满额度；不直接把总请求数翻倍。随后依据实际 RPM/TPM、429、内存和尾延迟调整。
- 同一场景浏览器操作完成后，来源复核与显示复核并行。任何一项失败都不能发布。
- 图表取证可以和其他节点正文生成重叠；图解编写以该节点正文及来源已核验为前提。
- 节点编写和全文覆盖检查并行准备；全文检查失败时，不能将局部通过误标为全篇完成。
- 模型、OCR、浏览器各有独立并发上限；对话保留响应额度，长文任务不能堵住 Copilot。
- 浏览器工作进程可复用，但每幅使用独立 context、重新设置路由和视口并关闭 context，避免上一个测试的侧栏/视口/存储状态污染下一幅。

## 4. 缓存、局部修复和更紧凑的输出

### 4.1 按内容缓存，而不是仅按 job_id 缓存

| 产物 | 缓存键至少包含 | 失效规则 |
|---|---|---|
| 文字/OCR IR | 文件 hash、页码/区域、解析器/OCR模型及配置 | 文件或对应解析规则变化 |
| 原页视觉证据 | 文件 hash、页码/区域、视觉模型、取证提示版本 | 对应图页或取证规则变化 |
| 节点证据包 | 原句 hash、表图/注释依赖、节点内容版本 | 任一依赖改变 |
| 图解草稿 | 节点和证据 hash、策划、作者模型、skill 版本 | 内容、策划或编写规则变化 |
| 检查结果 | 产物 hash、证据 hash、对应检查器/模型/提示版本 | 对应依赖改变 |

不同任务命中同一缓存时采用单次执行和等待共享结果，防止重复调用。用户对话、个人概念库、页面补充不进入图解内容缓存，也不能被缓存覆盖。缺失、失败和不确定结果不能缓存成成功。

开发测试另有“强制重新检查”选项。用于验证新检查器的批次必须重新运行检查，不允许缓存把回归隐藏掉。

### 4.2 只修出错的阶段与依赖

- 视觉接口超时、格式错误或输出截断：保留图稿，重新运行相应检查。
- 标签裁切：修布局，重新跑受影响的浏览器、显示检查和变更后的来源复核。
- 数据或逻辑错误：修对应图稿及所有依赖状态，重新走全部相关质量门。
- 正文一个节点改变：只使依赖它的图解失效；不重生其他章节。
- 只有依赖和检查版本完全相同时才复用旧通过结果。手工修复也不能绕过检查。

### 4.3 减少机械输出，不删解释内容

- 维持文档专属 HTML/SVG/CSS；受信运行器、来源按钮、状态说明区和公共样式由代码生成，不要求模型重复输出。
- 场景状态仍独立恢复到基础 DOM，再应用本状态差异；避免每个状态重复列出所有不变属性。压缩前后必须有等价状态证据。
- 长输出拆成基础图稿与状态绑定两个有明确契约的产物，按实际大小决定是否拆分，不能固定为每幅增加两次模型调用。
- 对长度风险做输入/输出预算预估；达到风险阈值时局部拆分，不先生成一份必然截断的巨型 JSON。
- 不建设学科组件库、不用固定页面模板取代内容策划，不改变用户当前授权的呈现方向。

## 5. 长 PDF：全文索引、论证分层、原文取证

页数只影响资源估计；章节结构、有效 token、表图密度、跨章依赖和扫描比例决定实际工作划分。不能用“超过某页数只读摘要”处理。

### 5.1 每页进入覆盖账本

先建立页码/文字块/标题层级/图表/公式索引，保留物理页锚点。覆盖账本区分：已解析、待 OCR、识别存疑、参考文献/附录、已进入论证节点、仍有缺口。

每页必须有可追踪归属；不要求每页都生成一幅交互，但核心结果、反例、条件和限制不能遗漏。扫描页超过预算要排队续做或明确未完成，不能悄悄跳过后标为完整。

### 5.2 章内计划与全篇关系分别组织

先在真实章节/小节边界和 token 预算内并行建立章内论证计划，再合并全篇问题、方法、证据、结论与局限。

归纳只用于找路和建立依赖，不能成为图解中数字/公式的最终证据。每个关键主张仍指向原文字块/原图；遇到前文定义、脚注、附录和跨页表格，沿依赖取回实际片段。

不把整份长文强塞成目前常见的 5–10 个大节点，也不固定整份只做 2–3 幅图。节点数随论证结构扩展，交互数量由理解收益决定；必要讲解保留完整。

### 5.3 为每个节点生成证据包

证据包包括：原句、图表及表注、变量定义、数字单位/时点/总体/有效位数、条件/反例/限制、相关原图区域、所需前置节点。

由可追踪依赖选择上下文，去掉重复机械元数据；不能仅用向量 top-k 或字符截断决定核验范围。若所需原文仍超过单次预算，就按子主张拆分核验并汇总，缺一个必需依赖都不能视为通过。

图解只读取与它相关的证据包。事实复核读取全部实际显示状态和所需来源；DOM bbox、重复 CSS 等留给本地检查器，不反复塞进事实上下文。

### 5.4 连续生成、渐进可读，完成标准不变

全篇论证骨架确定后，各章节并行生成正文和呈现。前面的完整章节通过后即可阅读；后面的进度保持可见。当前阅读章节可提高调度优先级，同时为全篇剩余章节保留执行额度。

状态至少区分：全文索引完成、章节生成中、部分章节可读、全文核心覆盖通过、必要交互检查通过。只有最后两项均满足，才能显示首轮完整交互讲解已完成。

最终仍是一篇文档、一条可从头读到尾的阅读主线，按既有节点和源页回查；内部切分不要求用户拆文件、不拆个人概念库和对话。

### 5.5 当前上限必须如实处理

目前上传上限是 20 MB / 120 页，默认 OCR 预算 30 页。大于 120 页尚未支持，不能只改限制文案就声称可处理数百页。

先在现有上限内完成流水线、分层论证和可恢复任务；再将长文解析/页图转为分批读取及持久化，实测内存、存储、模型额度、超时和断点恢复后，逐步开放更长文档。具体新上限由实测确定。

## 6. 质量不退化的发布门槛

| 维度 | 必须保留的检查 |
|---|---|
| 全文完整 | 全文覆盖账本、核心论证/结论/边界无缺失，不能靠少做图提速 |
| 来源忠实 | 实际原句/原图、每个状态的单位/总体/时点/精度/条件；摘要不能代替原文 |
| 操作有效 | 每个可达状态实际操作，检查可见图形/数据/关系变化；说明文字变化不算 |
| 显示质量 | 标签遮挡、裁切、轴/图例/单位、320–1440 宽度和人工代表抽查 |
| 发布一致 | 内容/来源/运行器版本匹配，未核验和过期产物不可发布 |
| 原功能 | Copilot、知识递归、概念库、PDF 回查、补充预览/应用/撤回全部回归 |
| 增量正确 | 修改某一依赖后应失效的任务确实失效，其他已通过任务不重复生成 |

采用冻结输入和计划范围的前后对照。不能拿热缓存对比旧版冷启动，也不能把失败后提前结束算作更快成功。基准分开统计：冷启动、缓存命中、局部重试、单篇无排队、10 篇吞吐，以及用户实际排队时间。

新增 queue_wait、model_wait、provider_elapsed、parse/OCR、evidence、author、browser、visual、fidelity、repair、time_to_first_verified_section、time_to_complete 等独立指标；报告 P50/P95、调用量、token、429/超时和失败率。

测试每批先全部完成并记录，再集中修复。原 10 篇之外增加真实长文、跨章定义、跨页表格、混合扫描和后部重要结论样本；数百页支持上线前必须实际覆盖目标长度。学习效果不能仅由浏览器通过推断。

## 7. 实施顺序与效率目标

1. 当前冻结批次跑完，保存全部问题和基线。补齐细分计时，先区分队列、模型和浏览器耗时。
2. 场景级流水并行、独立质量检查并行、浏览器进程复用；保持当前模型和总额度，验证同一计划的全部状态。
3. 按内容缓存与失败阶段重试，删去模型上下文中的重复元数据；逐项验证缓存失效与修复依赖。
4. 基础图稿/状态输出优化，以可观察状态等价和内容完整性作为门槛。
5. 长文覆盖账本、章内/全篇分层计划、节点证据包与渐进发布；先验证现有页数范围，再开放更大文件。
6. 完成质量和性能对照后，纳入原交互呈现默认发布。原有业务语义不变。

研发目标：同等计划范围下先争取冷启动完整生成时间下降 30% 以上；热缓存和仅审查重试应避免重新编写图稿。这是待验证目标，不是已实现结果或用户耗时承诺。首次可读时间改善与完整生成时间改善必须分别报告。
